What each column means, and the real ceiling

total / request is input + output, because both of Groq's limits count both — an input-only figure reads as headroom the budget does not have. Input is broken out beneath it because input is the half that grows silently: #212 measured prompt input growing 18.5% per call, and #266 was a 413, a pure input-size failure. Total is the ceiling; input is the regression signal. of one bucket weighs one provider call against {{ "{:,}".format(ops.tpm_per_model) }} TPM for a single model — per call, because that is how the bucket is charged. For a fanned-out feature the two differ: a rashifal request is ~61,600 tokens in total but 5,133 on any one call, and quoting the request against a per-minute bucket would print a percentage no request could mean. The chain is two models with separate buckets, so a route near 100% cannot run twice concurrently on the same one whatever its hit rate looks like. calls counts cached requests, which is not the same as LLM calls: a rashifal request is one document generated by twelve parallel provider calls, and the row says so when the two differ. A measured row divides by the provider calls that were actually sized; an est row has no provider usage in the window and divides by misses instead. Either way a cache hit spends no tokens, so dividing by total calls would make every prompt look cheaper as the cache warms. Until #473 these columns were not measured at all — cache.estimate_tokens(text) × 2, input defined as twice a guess at the output, which is why every route used to report a flawless 2:1 and why rashifal read 7,692 input tokens for a job that measures ~38,500. saved by cache is hits × the mean cost of a miss on that route, counted per request: a hit avoids a whole document, all twelve calls of a rashifal, not one. A feature at 0% cache pays full price every request. avg miss is wall-clock per generated reading and covers only days recorded since #355; earlier days stored one global figure, so a feature with none shows —, never 0.
